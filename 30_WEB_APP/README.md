# KIMA EIS — تطبيق الويب (30_WEB_APP)

منصة التنفيذ: HTML/CSS/JavaScript خام — بدون بناء، بدون Gradle، بدون Node.
معتمد بموجب `00_CONTROL/ACR/ACR-001-web-platform-shift.md`.

## التشغيل من هاتف أندرويد — بدون أي خادم

1. انسخ مجلد `30_WEB_APP` بالكامل (الملفات الستة) إلى تخزين الهاتف، مثلًا داخل
   `Download/KIMA/` عبر أي تطبيق ملفات أو نقل USB.
2. افتح `index.html` من تطبيق إدارة الملفات؛ سيُفتح تلقائيًا في المتصفح
   الافتراضي (Chrome يُفضَّل — تم التحقق عليه فعليًا).
3. التطبيق يعمل فورًا: لا اتصال إنترنت مطلوب، لا تثبيت مطلوب.
4. البيانات تُخزَّن داخل `IndexedDB` الخاصة بالمتصفح على هذا الجهاز، وتبقى
   بعد إغلاق المتصفح وإعادة فتح الملف.

**تحذير:** إن حذفت المتصفح بيانات التصفح/الموقع (Clear browsing data لهذا
الأصل)، تُحذف قاعدة البيانات المحلية معها. لا نسخ احتياطي تلقائي في R1 — هذا
مخطط له في نطاق `13_BACKUP` لاحقًا.

## التشغيل كتطبيق ويب تقدمي (PWA) — اختياري

يتطلب استضافة الملفات عبر `http(s)://` (مثل GitHub Pages أو أي استضافة
استاتيكية). عند الفتح عبر رابط ويب:
- يظهر خيار "إضافة إلى الشاشة الرئيسية" من قائمة المتصفح.
- بعد التثبيت، يعمل التطبيق بأيقونة مستقلة وبدون شريط عنوان المتصفح.
- يعمل الـ Service Worker تلقائيًا لتخزين واجهة التطبيق مؤقتًا، فيبقى قابلاً
  للفتح حتى لو انقطع الإنترنت لاحقًا (بعد أول تحميل ناجح).

هذا الوضع **غير مفعّل ولا ضروري** عند الفتح المباشر عبر `file://` — الكود
يتحقق من البروتوكول ولا يحاول تسجيل الـ Service Worker إلا عند الاستضافة.

## البنية التقنية

| ملف | الدور |
|---|---|
| `index.html` | الهيكل، دعم RTL كامل (`dir="rtl"`, `lang="ar"`) |
| `styles.css` | التصميم — لوحة بيانات هندسية داكنة، بدون أي اعتماد شبكي |
| `db.js` | طبقة الوصول لـ IndexedDB، تُطبّق `04_DATA/INDEXEDDB_SCHEMA_R0.md` حرفيًا مع فرض التكامل المرجعي يدويًا |
| `app.js` | منطق الواجهة، الربط بـ `db.js`، بدون أي اعتماديات خارجية |
| `manifest.webmanifest` | بيانات تثبيت PWA |
| `service-worker.js` | تخزين مؤقت لواجهة التطبيق عند الاستضافة فقط |

## نطاق R1-001 الحالي

يُطبَّق فعليًا: إنشاء عنصر هندسي (`entity`) + معرّفات مصدر متعددة
(`entity_identifier`) مع فرض التفرّد على `[namespace, identifier]`، وسجل
تتبع أساسي لكل عنصر. بقية الجداول (`relationship`, `evidence`,
`standard_mapping`, `change_event`, `source`) معرّفة في `db.js` (البنية جاهزة
عبر `openDb`) لكن واجهاتها ومنطق عملها لم يُبنَ بعد — مهام تالية.

## استيراد Excel — التعرّف التلقائي على الأعمدة (ADR-012, ADR-013)

عند استيراد ملف `.xlsx`/`.xls`، يحاول النظام التعرّف تلقائيًا على أعمدة
`entity_type` و`canonical_name` من أسماء أعمدة شائعة (`Tag Number`,
`Asset Type`, `Tag_ID`, `Functional Type`, ...، عربي وإنجليزي). إن فشل
التعرّف التلقائي، تظهر لوحة ربط يدوي لاختيار العمود المناسب يدويًا —
هذا سلوك متوقّع لملفات لا تحتوي عمود نوع واضح (مثال حقيقي: شيت
`06_Instruments` في ملفات K103 DEXPI/CFIHOS لا يحتوي عمود نوع موثوق —
أقرب مرشح متاح فيه قيمته `no_match` في أكثر من ربع الصفوف، فتُرك للربط
اليدوي عمدًا بدل تعيينه تلقائيًا وإدخال بيانات غير صحيحة بصمت).

بيانات العلاقات (`relationship`) — مثل شيتات "Piping Connections" أو
"Relationships" — لا تُستورد من Excel حاليًا؛ إدخالها متاح فقط يدويًا عبر
لوحة العلاقات في الواجهة (راجع `00_CONTROL/V3_GAP_REGISTER.txt`, M-16).

## الاختبار

تم التحقق فعليًا (ليس افتراضًا) عبر متصفح Chromium حقيقي (headless)، في
كلا الوضعين (`file://` و`http://`)، لجميع معايير القبول الثمانية في
`00_CONTROL/tasks/R1-001-TASK_CONTRACT.md`. راجع
`00_CONTROL/tasks/R1-001-TASK_RESULT.md` للتفاصيل والأدلة.
